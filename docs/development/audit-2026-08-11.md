# Audit: Level creation, per-child placement, deletion, deployment

Questions the Document Owner asked to be **audited before implementation**. Each
ends at a decision, not at a change. Nothing here has been implemented.

The **addendum at the end supersedes item 1**: audited on its own, Level creation
looked like a choice between three workarounds; audited against the whole
educational-structure model, it has one clean answer.

---

## 1. Level creation asks for a branch, and removing it breaks an invariant

### What is actually there

`createLevel` (`backend/src/services/level.service.ts`) creates a Level **and its
first Administrative Group in one transaction** (TD-4.6b). The branch is not
stored on the Level — the form's own hint says so — it is the branch of that
first group. The Owner's hierarchy is therefore already the *data* model:

```
Category → Level → AdministrativeGroup → Branch
```

`Level` has `categoryId` and no branch column. Nothing to fix in the schema.

### Why the branch is asked for anyway

**§4.1: approval IS the enrolment, and an enrolment needs a group.** A Level with
no group can admit nobody. TD-4.6b makes the pair atomic so the state cannot
arise, `LAST_GROUP_IN_LEVEL` refuses deleting the last group, and
`levelsWithoutGroups()` exists to assert the invariant — its own comment reads
*"after bootstrap this must always be empty."*

**It is not empty. 18 of 20 live Levels have no group.** Those Levels did not
come through `createLevel`; they came from seeds or fixtures. That is the direct
cause of the broken approval button (item 4), now worked around in the UI by
excluding unassignable Levels.

### The conflict, stated plainly

Removing the branch from the form means Levels can exist with no group — which is
**exactly the state TD-4.6b was written to prevent**, and exactly the state that
just produced a dead button in the approval queue. The Owner's model is right;
the invariant is also right; they cannot both hold in their current form.

### The three coherent resolutions

| | Model | Cost |
|---|---|---|
| **A** | Level created alone. The invariant is **retired**: a Level may have no group, and it is simply not offered for placement until one exists (the UI already behaves this way since item 4). Groups are created on `/admin/groups`. | The approver can be blocked by a missing group, and must leave the queue to fix it. Honest, and already the live behaviour. |
| **B** | Level created alone, and **approval can create the group inline** — the approver picks a branch and a group is made in the same transaction as the enrolment. | Preserves "an approver is never stuck". More surface: approval gains a write it did not have, inside TD-4.2's transaction. |
| **C** | Keep TD-4.6b, but **make the branch optional** with a clearly-worded second step: create the Level now, add its first group when you know the branch. | Smallest change; still leaves the invariant violated by the same door, so it is A with extra words. |

> **Superseded by the addendum.** Read that first: moving the branch onto the
> enrolment makes option A correct *and* removes the cost column, because the
> approver is no longer blocked by a missing group at all.

**Recommendation: A**, plus a data repair for the 18 Levels. It matches the
Owner's stated hierarchy exactly, it is what the interface already does, and it
removes a rule the live database has never actually satisfied. B is a defensible
second and could be added later without redoing A.

**This needs an SRS revision** — TD-4.6b is normative and would be retired or
narrowed. It is not a form edit.

**Also required either way:** a decision about the 18 existing Levels. Give them
a group (which branch?), or leave them unplaceable. That is a data decision, not
an engineering one.

## 2. Per-child branch and category — no migration needed

### What is actually there

`child_application` **already carries `requested_branch_id` and
`requested_category_id` per row** (R62 for the category, R64 for the branch). The
data model already supports what the Owner asked for. Approval already decides
one child at a time and already reads that child's own values.

### What is wrong

Three places treat them as **request-level**:

| Place | What it does |
|---|---|
| `parentChildRegistrationSchema` | one `branch_id` + one `category_id` for the whole request |
| `registration.service.ts` | copies both onto every child |
| `/profile/register-child` | collects one of each per submission |

So a parent registering a child for الطفل at تاركة and another for اليافعون at
أمرشيش cannot express it, even though the rows could hold it.

### The change, if approved

* `childCore` gains `requested_branch_id` and `requested_category_id`;
* the top-level `branch_id` **stays**, because it is the *applicant's own*
  `intended_branch_id` (R39) and is a different fact;
* the top-level `category_id` is **removed** from the parent+child path — a
  parent is admitted to no Level, so it existed only to be copied;
* both forms move the two controls into the shared `ChildFields`.

**No migration. No schema change.** It amends R62's *"one stage for the family,
chosen once"* and R64.2's *"the family's chosen branch is copied onto each
application"*, so it needs a revision — but the storage is already correct.

## 3. Deletion: what exists today

### The inventory

**45 models. 28 carry `deleted_at`; 17 do not.**

**Soft-deletable (28):** AdministrativeGroup, Branch, Category, ChildApplication,
CourseScheduleStaff, EducationalContent, Enrollment, Event, Exam, ExamStaff,
FamilyLink, HijriMonthStart, Level, LevelSubject, LevelSurah, QuranProgressLog,
RecurringCourseSchedule, Room, Session, SessionContent, SessionStaff,
StudentSocialProfile, StudentTeachingGroup, Subject, TeachingGroup, Trash, User,
UserBranchRole.

**Not soft-deletable (17), and mostly for good reasons:**

| Model | Why it has no `deleted_at` |
|---|---|
| `AuditLog` | **Accountability.** TD-8's trail cannot be editable by the people it records. |
| `ConsentRecord` | §4.1a — a consent decision is evidence. Revocation is a *field*, not a deletion. |
| `Grade`, `StudentExamSubmission`, `StudentSurahProgress` | Academic record. |
| `UserIdentity`, `RefreshToken`, `ConsumedToken` | Security state; removal is revocation, and it is immediate by design. |
| `Role`, `SystemSetting`, `AcademicYear`, `QuranSurah` | Reference data the platform depends on. |
| `RateLimitCounter` | Ephemeral. |
| `EventBranch/Category/Level/AdministrativeGroup` | Join rows; they follow their parent. |

### Restore and purge are already **narrower** than soft delete, deliberately

* `RESTORABLE` — **6 types**: Branch, Category, Exam, HijriMonthStart, Room,
  Subject.
* `PURGEABLE` — **17 types**, with declared cascade children.

`trash.service.ts` states the rule this follows: *restorability is enumerated,
never inferred*, because restoring a row whose dependants were cascaded is how a
half-restored graph appears. The service already reports **why** a row is not
restorable or not purgeable, as stable codes.

`User` is deliberately **neither** restorable nor purgeable
(`ACCOUNTABILITY_RECORD`) — R54's unapproved draft is about *anonymisation*, not
row destruction.

### The honest assessment

**The platform does not need a generic "delete anything" mechanism, and adding
one would be a mistake.** The existing model already answers the Owner's goal for
the entities where it is safe:

> soft delete → record who/when → leaves operational views → appears in Trash →
> Super Admin restores → Super Admin purges *only when allowed*

What is genuinely missing is narrower than "everything":

1. **`RESTORABLE` covers 6 of 28 soft-deletable types.** The other 22 can be
   soft-deleted and then only purged or left. Widening it is a per-type question
   (what must be re-created, in what order, and what was cascaded), not a switch.
2. **BR-15's 90-day retention is documented and not in force** — `content.quarantine-purge`
   was never built, so quarantine is permanent storage (already on `TASKS.md`).
3. **Backups are outside the model.** A purge removes rows from the live
   database; the offsite Moroccan backups (§19) still hold them until they age
   out. Any statement to a person that their data is *gone* must account for
   that, and today nothing does. **This is a compliance question, not an
   engineering one.**

**Recommendation:** do **not** draft a platform-wide "delete anything" revision.
Instead treat it as three separate, smaller decisions — widen `RESTORABLE`
type-by-type with the cascade written down; switch on the retention job; and
settle the backup statement with the CNDP work already pending. Each is safe on
its own; the generic mechanism is not.

## 4. Deployment readiness: **not ready, and not the intended architecture**

### What is actually deployed at `bodouralamal.vercel.app`

`docs/operations/deployment.md`:

> Pushing to `develop` triggers an automatic Vercel build of the frontend, in a
> **fixture-pointing configuration only. It calls no real backend.**

And §19.0: *"Vercel staging reviews UI against MSW mocks only — zero CORS
allow-listing anywhere."*

**It is a UI preview against mocks.** There is no API, no database, no object
storage and no OAuth there, and by design there never has been.

### What the platform actually requires

The production topology (§3.1, `docs/operations/deployment.md`) is **a single
Moroccan VPS running docker-compose**: nginx terminating TLS and routing
same-origin paths (`/`, `/api/v1/`, `/storage/`), the Express API, PostgreSQL 18,
MinIO, and pg-boss workers.

**Same-origin routing is not a deployment detail — it is load-bearing.** TD-12
puts the refresh token in an `HttpOnly; SameSite=Lax` cookie and the access token
in a header; §4.1b's OAuth callback is a server redirect on the same origin.
Splitting the frontend onto `*.vercel.app` and the API elsewhere breaks the
cookie, the callback and the storage proxy at once, and the SRS explicitly
forbids the CORS allow-listing that would be needed to paper over it.

### Assessment

| Question | Answer |
|---|---|
| Is the frontend deployed independently? | Yes — as a **mock-backed preview**. |
| Where does the API/database run? | Nowhere yet. Local compose only. |
| Environment variables configured there? | Not for a real backend; there is none to configure. |
| Does production match local? | Local **is** the production topology. Vercel is not. |
| Can Vercel host the backend requirements? | Not as specified: PostgreSQL, MinIO and pg-boss workers are long-lived services. |
| Are migrations safe to apply? | Untestable — no production database exists. |
| Auth redirects / cookies / CORS correct? | Cannot be, across two origins, without violating TD-12 and §19.0. |
| Is it the complete platform? | **No. It is a frontend preview.** |

**Verdict: do not deploy the platform to Vercel.** Doing so would publish a
frontend that cannot sign anyone in, against an architecture the SRS rules out.

**What deployment actually needs**, in order: a Moroccan VPS (§19 requires
Moroccan hosting), DNS and TLS, the compose stack, `SUPER_ADMIN_EMAIL` seeded
once, real Google OAuth credentials with the production redirect registered, the
backup pipeline with a **tested restore**, and the dress rehearsal on the VPS
itself. None of that is blocked by code; it is blocked by infrastructure that
does not exist yet.

**Owner decision required:** whether Vercel remains the mock-backed staging
preview it was designed as (recommended — it is useful for exactly that), or
whether the association wants a different production host, which is a hosting and
compliance decision given §19's Moroccan-hosting requirement.

# Addendum: the educational-structure model

Audited on request, **not implemented**. The question was whether the SRS and
schema can support: *Category → Level → optional Level Group*, *Subject →
optional Subject Circle*, with branch belonging to the operational assignment.

## Already supported — no decision needed

Four of the six statements in the model are **already the specification**, and
three are already the schema.

| Statement | Status |
|---|---|
| A Level belongs to a Category, not a Branch | **Already true.** `Level.categoryId`; there is no branch column and never was. The creation *form* asks for one, but it is the first group's branch (item 1 above). |
| A Subject is an independent primary entity | **Already true.** `Subject` carries `name` and `display_order` and nothing else; it reaches Levels through `LevelSubject`. |
| A Subject may have zero or more Circles | **Already specified, verbatim.** §7: *"It exists only when a Subject needs students split differently from the administrative roster. A Subject with no Teaching Groups in a Level is taught to the entire Level. **Creating Teaching Groups is not a prerequisite for teaching a Subject.**"* |
| A student attends a Subject directly when it is not split | **Already true.** A `StudentTeachingGroup` row exists only for a split Subject; otherwise Level enrolment + `LevelSubject` is the whole answer. `TeachingMode.entire_level` delivers it. |

**The Subject half of the model needs nothing.** R43 built it deliberately, and
§7 argues for it in the same words the Owner used.

## The conflict is one rule, and R43 took it on purpose

§7, Enrollment:

> **A student belongs to one or more Levels, and to exactly one Administrative
> Group inside each enrolled Level.**
> Level membership is never stored separately. It is the answer to
> `Enrollment → AdministrativeGroup → Level`. A `StudentLevel` entity was
> drafted and **withdrawn** (Revision 43).

Six things follow from it, and each is a conflict with the intended model:

1. `enrollment.administrative_group_id` is **NOT NULL**;
2. **TD-4.6b** — `createLevel` creates the Level *and its first group* atomically;
3. **TD-4.6d** — a bootstrap backfill puts `المجموعة 1` in every Level;
4. **`LAST_GROUP_IN_LEVEL`** — a Level may not lose its last group;
5. **a student's branch exists only through the group** — §5.2 and R43.3 both
   name the path `Enrollment → AdministrativeGroup.branch_id`, and **13 code
   sites read it**;
6. `entire_level` audience resolution filters students *by their group's branch*.

(5) is the load-bearing one. Make the group optional and a student in an
unsplit Level has **no branch at all** — which breaks Admin branch scoping,
teaching-group placement (R43.3 calls the group's branch *"a referent that does
exist"*), the Educational Library's own-branch ordering, and entire-level
audiences.

## The smallest coherent revision: the branch moves to the enrolment

One idea, and everything else falls out of it.

> **`Enrollment` carries `branch_id` directly.** The enrolment *is* the
> operational assignment, which is precisely where the Owner's model puts the
> branch. `administrative_group_id` becomes **nullable**: a subdivision, not a
> requirement.

Why this is small rather than sweeping:

* **It introduces no new concept.** No `StudentLevel` (R43 withdrew it, rightly
  — `Enrollment` already carries `level_id`). No new entity, no new join.
* **Agreement is enforced, not intended.** A composite FK
  `(administrative_group_id, branch_id) → AdministrativeGroup(id, branch_id)` is
  **exactly the trick R43 already uses** for `level_id`, and in PostgreSQL a
  composite FK with a NULL column is not enforced — so the ungrouped case needs
  no special handling and the grouped case cannot disagree.
* **`UNIQUE (student_id, level_id)` is unchanged** and still does its work.
* **The Owner's example survives intact**: groups keep their branch, so
  *مجموعة 1 → تاركة* and *مجموعة 2 → أمرشيش* read exactly as written.
* **One rule changes in 13 places** — "the student's branch" stops being a join
  and becomes a column. §5.2 and R43.3 already state it as *one* rule, so there
  is one sentence to edit, not a policy to re-derive.
* **The 18 group-less Levels stop being broken.** They become legal, students can
  be enrolled directly, and the approval dead-end disappears at the root rather
  than being filtered around in the UI.

What retires with it: **TD-4.6b** (Level + first group atomic), **TD-4.6d** (the
backfill), and **`LAST_GROUP_IN_LEVEL`**. Deleting a group with members stays
refused by `ENROLMENTS_EXIST`, which already exists and is the rule that actually
protects anybody.

## Terminology: keep the entities, fix the labels

The Owner's words are *Level Group* and *Subject Circle*; the model's are
**Administrative Group** and **Teaching Group**.

**Recommendation: keep the entity names, change the Arabic labels.** The current
names encode §20 rule 22's distinction — *organisation* versus *delivery* — which
is the one thing this model must not blur, and renaming would touch the SRS, the
schema, 40+ files and every test for a vocabulary gain the interface can deliver
on its own. The interface already says «مجموعات المستويات»; «حلقات المواد» is the
matching label for Teaching Groups.

## Decisions needed

**1 — Adopt the model?** *(the only one that must be answered)*
Recommend **yes**. Four of six statements are already specified; the sixth is one
R43 took explicitly and can be revisited explicitly. The current rule is already
violated by the live database in 18 of 20 Levels, and it produced a dead button
in the approval queue this week.

**2 — Branch on `Enrollment`, or keep the group mandatory?**
Recommend **branch on `Enrollment`**. It is the Owner's own sentence made
literal, it is one column plus one composite FK, and it removes a two-hop
derivation that 13 sites repeat today. The alternative is to keep the group
mandatory and accept artificial groups, which is what was asked to be removed.

**3 — Existing data.** Every live enrolment can be backfilled from its group's
branch, so the migration is **derivable and non-destructive** (TD-6b expand →
backfill → contract). No data decision is needed. **Unless** the Owner wants the
18 group-less Levels given groups anyway, in which case that is a separate
operational choice, not a prerequisite.

**4 — Terminology.** Recommend **labels only**, as above. Say the word if the
entity names should change and it becomes a much larger, mechanical revision.

**5 — Scope of the revision.** Recommend it covers **only** the Level side.
The Subject side needs no text; restating it would risk drifting from §7's
existing wording, which is already correct.
