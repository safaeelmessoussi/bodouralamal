# Technical design constraints

Nineteen constraints (TD-1 … TD-16, plus TD-6a, TD-6b, TD-11a) on *how the system must be built*; [business rules](business-rules.md) say what the domain requires. Authoritative text: SRS §13.

| TD | Rules | Code · explained |
|---|---|---|
| <a id="td-1"></a>**TD-1** State machines | Exhaustive lifecycles (account status, family links, grades, exam submissions, content visibility); unlisted transitions → `STATE_CONFLICT`; changes only via validating service methods, never a raw column update. `Rejected` terminal (re-registration needs staff action); `Approved` family link terminal, revocation = soft delete re-checked per request | `services/` · [Backend](../architecture/backend.md) |
| <a id="td-2"></a>**TD-2** Role-permission matrix | Normative, enforced server-side on every endpoint; UI hiding is never enforcement. Admin within assigned branch scope; Super Admin unscoped by role; Teacher within assigned groups; Parent actions on child data need per-request child verification | `policies/` · [Identity and access](../architecture/identity-and-access.md#authorization), [Users and roles](../overview/users-and-roles.md) |
| <a id="td-3"></a>**TD-3** API route registry | Normative for currently documented milestones; the seed for the generated contract, later milestones add through revisions. TD-3.8 = error envelope and code catalogue | `app.ts`, `controllers/` · [API](../architecture/api.md); [API endpoints](api-endpoints.md), [Error codes](error-codes.md) |
| <a id="td-4"></a>**TD-4** Transaction boundaries | Fifteen single-transaction sequences (registration, approval bundles, soft deletes, quota-gated uploads, refresh rotation, logout, suspension-revokes-sessions). A job enqueue is an insert through the same transaction client: no committed mutation with a lost job, no job for an uncommitted mutation | `services/` · [Backend](../architecture/backend.md#transactions) |
| <a id="td-5"></a>**TD-5** Deletion and cascade | Per-entity, mostly prohibitive: branches, rooms, categories, levels, groups cannot be deleted while referenced. Un-enrolment never touches grades, submissions or progress logs | [Database](../architecture/database.md#soft-delete-and-cascade) |
| <a id="td-6"></a>**TD-6** Database constraints | Uniqueness, checks, collations, referential integrity are schema-enforced, not merely validated in code | [Database](../architecture/database.md#constraints-the-application-layer-cannot-be-trusted-with) |
| <a id="td-6a"></a>**TD-6a** Prisma migration workflow | Binding. Collations, checks, partial/functional indexes and triggers cannot be expressed in Prisma schema syntax: `prisma migrate dev --create-only`, then hand-write SQL; `prisma db push` prohibited in every environment; two CI guards | [Database](../architecture/database.md#hand-written-sql) |
| <a id="td-6b"></a>**TD-6b** Migration compatibility | Binding. Forward-only in production; data preserved; destructive changes follow expand–migrate–contract with the drop in a separate later migration; no direct renames (Prisma renders DROP + ADD) | [Database](../architecture/database.md#compatibility-policy) |
| <a id="td-7"></a>**TD-7** Background job catalog | Ten jobs with triggers, payloads, idempotency; exponential backoff, five attempts, dead-letter with Admin-visible failure. Quran coverage recalculation is synchronous, not a job. `session-recording-ingest` (R100): the verified provider callback persists and enqueues, never ingests; order verify staging object → server-side copy → content → link → relation → staging swept last | `jobs/` · [Background jobs](../architecture/background-jobs.md#the-catalog) |
| <a id="td-8"></a>**TD-8** Audit log coverage grid | Every listed action writes an audit row; the list is a minimum (add, never remove); sensitive reads audited (a child's case file). Retention 12 months for authentication rows, indefinite otherwise; purge selects on an enumerated allowlist AND age | `repositories/audit.repository.ts` · [Security](../architecture/security.md#auditing-as-a-security-control) |
| <a id="td-9"></a>**TD-9** Validation limits and storage naming | Field limits, upload caps, MIME allowlist, deterministic immutable key structure with a random hash segment | `validators/` · [Storage](../architecture/storage.md#keys) |
| <a id="td-10"></a>**TD-10** Pagination, sorting, search | Every list endpoint paginated: default 25, max 100, `{ data, meta }`; deterministic tiebreakers; substring search over generated normalized shadow columns, never per-row normalization; no fuzzy matching in the MVP; a composite document is not a list endpoint | `lib/pagination.ts`, `lib/search-normalize.ts` · [API](../architecture/api.md#pagination) |
| <a id="td-11"></a>**TD-11** Time, timezone, dates | Persisted timestamps UTC; group and event times are local wall-clock, not instants (Ramadan DST suspension); week starts Monday; Hijri display reproduces recorded official data, never an algorithm or offset | [Calendar and Hijri](../architecture/calendar-and-hijri.md#wall-clock-time-and-the-ramadan-trap) |
| <a id="td-11a"></a>**TD-11a** Non-functional targets | API reads p95 < 300 ms · Quran writes incl. synchronous recalculation p95 < 100 ms · presigned mint p95 < 150 ms · RPO ≤ 24 h / RTO < 1 h · 99 % monthly | [Performance and scale](../architecture/performance-and-scale.md#measurable-targets) |
| <a id="td-12"></a>**TD-12** Auth session, child context, presigned URLs | Token lifetimes and transport, rotation with the idempotent grace window, CSRF posture, high-risk endpoint freshness, JWT claims, OAuth flow state, onboarding token, email normalization, presigned TTLs, authentication failure semantics by mount | `middleware/authenticate.ts`, `lib/access-token.ts`, `services/refresh-token.service.ts` · [Identity and access](../architecture/identity-and-access.md) |
| <a id="td-13"></a>**TD-13** Configuration and environment catalog | The single authoritative variable list; `.env.example` generated from it in lockstep; rate limits, connection-pool budget, container memory pins; secrets have no defaults | `lib/config.ts` · [Configuration](../operations/configuration.md) |
| <a id="td-14"></a>**TD-14** Observability and health minimums | Health endpoint with per-component detail; structured JSON logs with propagated request id; no PII in logs; job failures surfaced to Admins | `controllers/health.controller.ts`, `middleware/request-context.ts` · [Observability](../operations/observability.md) |
| <a id="td-15"></a>**TD-15** Concurrency policy | Read-committed everywhere; optimistic locking on staff-edited entities, `SELECT … FOR UPDATE` on check-then-write invariants, first-wins on transitions and unique races; never escalate isolation for a missing lock; never surface a conflict as a 500 | `repositories/optimistic-lock.ts` · [Backend](../architecture/backend.md#concurrency) |
| <a id="td-16"></a>**TD-16** Degraded operation | Per-dependency blast radius and required behaviour; the system never fabricates success | [Resilience](../operations/resilience.md#degraded-operation) |
